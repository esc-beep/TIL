# CHAPTER 4 핵심 실행 방법 1: 모든 것을 코드로 정의한다

## 4.1 코드로 정의할 수 있는 것

코드로 정의해야 하는 몇 가지 항목은 다음과 같다.
- 인프라 스택: 인프라 클라우드 플랫폼에서 프로비저닝된 구성 요소 모음
- 서버 구성 요소: 패키지, 파일, 사용자 계정, 서비스
- 서버 역할: 단일 서버 인스턴스에 함께 적용되는 서버 구성 요소
- 서버 이미지 정의: 여러 서버 인스턴스를 빌드할 수 있는 이미지
- 애플리케이션 패키지: 컨테이너를 포함해 배포 가능한 애플리케이션 아티팩트의 빌드 방법 정의
- 딜리버리 서비스를 위한 설정과 스크립트: 파이프라인과 배포 포함
- 운영 서비스의 구성: 모니터링 등 포함
- 유효성 검사 규칙: 자동화된 테스트와 규정 준수 규칙 포함

<br>

코드를 사용하지 않는 폐쇄형 인프라 자동화 도구는 사용할 수 있는 실행 방법과 워크플로가 제한적이므로 TDD, CI, CD와 같은 애자일 엔지니어링을 사용하기 어렵다.<br>
또한 인프라를 코드로 정의하는 경우에는 코드를 버전 관리 시스템에 저장해 다음과 같은 장점을 얻을 수 있다.
- 추적 가능성: 변경 내역, 변경한 사람, 이유 제공
- 롤백: 이전과 동일하게 복원하는 기능 제공
- 연관성: 태그, 버전 번호 등을 사용해 여러 부분의 관계 파악 가능
- 가시성: 커밋된 변경 내역을 확인해 장애의 원인 확인 가능
- 행동 가능성: 커밋된 변경에 대해 자동으로 작업을 트리거해 CI 작업과 CD 파이프라인을 가능하게 함

단, 비밀 정보의 경우에는 소스 코드에 넣지 않아야 한다.

<br>

## 4.2 인프라 언어

명령형 코드는 이벤트를 발생시키는 방법을 명시하는 명령어 집합이고, 선언형 코드는 발생 방법을 명시하지 않고 최종 결과의 형상만 명시한다. <br>
인프라 코드베이스에는 인프라 리소스 정의부터 유사한 리소스의 다른 인스턴스 구성, 상호 의존적인 여러 시스템의 프로비저닝 조정까지 다양한 문제가 포함된다. 일부는 선언형 언어를 사용하여 간단하게 표현할 수 있으나 복잡한 고려사항은 명령형 언어를 사용하는 것이 더 좋다.

### 4.2.1 인프라 스크립트

스크립트는 일반적으로 소프트웨어 개발 도구 모음(SDK)을 사용하여 클라우드 제공 업체의 API와 상호작용했다.<br>
Terraform과 같은 선언형 인프라 언어가 나타나기 전에는 인프라 스크립트를 통해 생성 내용과 생성 방법을 명시하고 로직을 구현했다.

### 4.2.2 선언형 인프라 언어

Ansible, Chef, CloudFormation, Puppet, Terraform을 포함한 많은 인프라 코드 도구는 선언형 언어를 사용해 서버에 있어야 하는 패키지, 사용자 계정, RAM, CPU 사양과 같은 인프라를 원하는 상태로 정의한다.<br>
코드를 지속적으로 적용하는 것은 인프라 코드의 일관성과 제어를 유지하기 위한 주요 실행 방법이다. 이 방법은 구성 드리프트를 방지하기 위해 인프라에 코드를 반복적으로 다시 적용하는 것을 포함한다.<br>
코드가 지속적으로 안전하게 적용되려면 **멱등성**이 있어야 한다. 멱등성을 만족하는 코드는 여러 번 다시 실행되더라도 출력이나 결과가 바뀌지 않는다.

<br>

### 4.2.3 프로그래밍 가능한 명령형 인프라 언어

선언형 코드는 항상 동일한 결과를 만들지만, 때때로 상황에 따라 다른 결과를 원할 수도 있다.<br>
대부분의 선언형 인프라 도구는 언어를 확장하여 명령형 프로그래밍 기능을 추가한다. 예를 들어 Ansible은 YAML에 반복문과 조건을 추가했고, Terraform의 HCL 구성 언어는 조건문과 반복문을 포함하는 표현식ㅇ들 가진 하위 언어를 결합한다.<br>
Pulumi와 AWS CDK 같은 최신 도구는 인프라에 프로그래밍 언어를 사용하는데, 이러한 도구는 범용 프로그래밍 언어를 지원하고 호환성이 높으며 동적인 인프라 코드를 구현할 때도 유용한다.

<br>

### 4.2.4 선언형 언어 vs. 명령형 언어

선언형 코드는 원하는 시스템의 상태를 정의하는 데 유용하며, 높은 수준의 일관성을 유지하면서 반복적으로 생성해야 하는 인프라를 정의하는 데 사용된다.<br>
프로그래밍 가능한 명령형 언어는 라이브러리와 추상화 계층을 구축하는데 더 적합하며, 라이브러리 작성, 테스트와 관리를 더 잘 지원한다.

<br>

### 4.2.5 도메인 특화 인프라 언어

DSL은 특정 도메인을 모델링하도록 설계된 언어다. 정의된 항목과 밀접하게 연관되므로 코드를 더 쉽게 작성하고 이해할 수 있다.<br>
많은 인프라 DSL은 YAML이나 JSON과 같은 기존 마크업 언어의 확장으로 구축된다. 일부 DSL은 범용 프로그래밍 언어의 하위 집합으로 작성되었다.<br>
외부 DSL도 있으며 이는 다른 언어로 작성된 코드를 해석한다.

<br>

### 4.2.6 범용 언어 vs. 인프라 DSL

대부분의 인프라 DSL은 선언형 언어이다. JavaScript, Python, Ruby, TypeScript와 같은 범용 프로그래밍 언어의 가장 큰 장점은 도구 생태계가 존재한다는 것이다. 테스트 지원은 프로그램이 언어 생태계에서 특히 유용한 부분이다.<br>
라이브러리와 추상화 계층같이 많은 가변적인 출력을 생성하는 코드의 경우 단위 테스트가 필수적이므로 범용 프로그래밍 언어가 선호된다.

<br>

## 4.3 인프라를 코드로 정의하기 위한 구현 원칙

1. 선언형 코드와 명령형 코드를 분리한다.
    - 요구사항 별로 선언형 코드와 명령형 코드를 분리한다.
2. 인프라 코드를 실제 코드처럼 다룬다.
    - 이해하고 유지하기 쉽게 인프라 코드를 설계하고 관리한다.
    - 코드 리뷰, 페어 프로그래밍, 자동화된 테스트처럼 애플리케이션 코드와 같은 코드 품질 관행을 따른다.
    - 기술 부채를 인식하고 최소화하기 위해 노력한다.

인프라 코드는 항상 정확하고 최신 상태로 유지되는 시스템 기록이므로 문서의 역할을 일부 대체할 수 있다.<br>
또한 아키텍처 결정 기록(ADR)을 마크업 언어로 작성하고 Git과 같은 소스 코드 관리 시스템을 사용하여 문석 이력을 관리하는 것도 좋은 방법이다.
