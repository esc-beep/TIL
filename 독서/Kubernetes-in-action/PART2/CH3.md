# 3장. 파드: 쿠버네티스에서 컨테이너 실행

## 3.1 파드 소개

IPC(Inter-Process Communication) 혹은 로컬 파일을 통해 통신하는 여러 프로세스로 구성돼, 같은 노드에서 실행해야 하는 애플리케이션을 상상해보자.<br>
컨테이너는 단일 프로세스를 실행하는 것을 목적으로 설계했다. 단일 컨테이너에서 관련 없는 다른 프로세스를 실행하는 경우 모든 프로세스를 실행하고 로그를 관리하는 것은 모두 사용자 책임이다.<br>
단일 컨테이너에서 여러 프로세스를 실행하는 경우 개별 프로세스가 실패하는 경우 자동으로 재시작하는 매커니즘을 포함해야 하고, 프로세스 별 로그를 구분하기 힘들다.<br>
따라서 각 프로세스를 자체의 개별 컨테이너로 실행해야 한다.

여러 프로세스를 단일 컨테이너로 묶지 않기 때문에 컨테이너를 함께 묶고 하나의 단위로 관리할 수 있는 구조가 파드이다.<br>
컨테이너 모음을 사용해 밀접하게 연관된 프로세스를 함께 실행하고 단일 컨테이너 안에서 모두 함께 실행되는 것처럼 거의 동일한 환경을 제공할 수 있으면서도 이들을 격리된 상태로 듀지할 수 있다.<br>
그룹 안에 있는 컨테이너가 특정한 리소스를 공유하기 위해서는 각 컨테이너가 완벽하게 격리되면 안된다.<br>
쿠버네티스는 파드 안에 있는 모든 컨테이너가 동일한 리눅스 네임스페이스를 공유하도록 도커를 설정한다.<br>
파드의 모든 컨테이너는 동일한 네트워크 네임스페이스와 UTS 네임스페이스 안에서 실행되기 때문에, 같은 호스트 이름과 네트워크 인터페이스, 동일한 IP 주소와 포트를 공유한다.<br>
따라서 동일한 파드 안 컨테이너에서 실행 중인 프로세스가 같은 포트 번호를 사용하는 경우 포트 충돌이 발생할 수 있다.<br>
파드 안에 있는 모든 컨테이너는 동일한 루프백 네트워크 인터페이스를 갖기 때문에 컨테이너들이 로컬호스트를 통해 서로 통신할 수 있다.이는 LAN에 있는 컴퓨터 간의 통신과 비슷하다.<br>
파드는 논리적인 호스트로서 컨테이너가 아닌 환경에서의 물리적 호스트 혹은 VM과 매우 유사하게 동작한다. 동일한 파드에서 실행한 프로세스는 각 프로세스가 컨테이너 안에 캡슐화되어 있다는 점을 제외하면 같은 물리적 혹은 가상머신에서 동작하는 것과 동일하다.<br>
하지만 컨테이너 파일시스템은 컨테이너 이미지에서 나오기 때문에 기본적으로 파일시스템은 다른 컨테이너와 완전히 분리된다. 이 때문에 볼륨으로 컨테이너가 파일 디렉터리를 공유한다.

모든 것을 파드 하나에 넣는 대신에 애플리케이션을 여러 파드로 구성하고, 각 파드에는 밀접하게 관련 있는 구성 요소나 프로세스만 포함해애 한다.<br>
다계층 애플리케이션을 여러 파드로 분할하면 쿠버네티스가 각 파드를 다른 노드에 스케줄링해 infrastructure의 활용도를 향상시킬 수 있다.<br>
또한 쿠버네티스는 개별 컨테이너가 아닌 파드를 수평으로 확장하므로 컨테이너를 개별적으로 스케일링하는 것이 필요하다면 별도 파드에 배포해야 한다.<br>
여러 컨테이너를 단일 파드에 넣는 주된 이유는 애플리케이션이 하나의 주요 프로세스와 하나 이상의 보완 프로세스로 구성된 경우다.<br>
예를 들어 파드 안에 주 컨테이너는 특정 디렉터리에서 파일을 제공하는 웹 서버일 수 있으며, 사이드카 컨테이너는 외부 소스에서 주기적으로 콘텐츠를 받아 웹 서버의 디렉터리에 저장한다.<br>
사이드카 컨테이너의 다른 예제로는 로그 로테이터와 수집기, 데이터 프로세서, 통신 어댑터 등이 있다.

<br>

## 3.2 YAML 혹은 JSON 디스크립터로 파드 생성

쿠버네티스 리소스는 일반적으로 쿠버네티스 REST API 엔드포인트에 JSON 혹은 YAML 매니페스트를 전송해 생성한다.<br>
YAML 파일에 모든 쿠버네티스 오브젝트를 정의하면 버전 관리 시스템에 넣는 것이 가능해져, 그에 따른 모든 이점을 누릴 수 있다.<br>
[pod.yaml](files/pod.yaml)은 몇 부분으로 구성된다. 먼저 yaml에서 사용하는 k8s api 버전과 yaml이 설명하는 리소스 유형이 있고, 아래와 같은 일반적인 구조를 가진다.
- metadata: 이름, 네임스페이스, 레이블 및 파드에 관련된 기타 정보를 포함한다.
- spec: 파드 컨테이너, 볼륨, 기타 데이터 등 파드 자체에 관한 실제 명세를 가진다.
    - 포트의 경우 생략해도 연결 여부에는 영향이 없으나, 포트가 명시적으로 정의되어 있으면 포트에 이름을 지정해 빠르게 확인할 수 있다는 장점이 있다.
- status: 파드 상태, 각 컨테이너 설명과 상태, 파드 내부 IP, 기타 기본 정보 등 현재 실행 중인 파드에 관한 현재 정보를 포함한다.

`kubectl create` 명령으로 yaml 파일을 이용해 파드를 만들 수 있고, `kubectl get po kubea-manual -o yaml` 명령어로 파드의 전체 정의를 yaml로 확인 가능하다.

컨테이너화된 애플리케이션은 표준 출력과 표준 에러에 로그를 남긴다. 이를 통해 사용자는 다른 애플리케이션 로그를 간단하고 동일한 방식으로 볼 수 있다.<br>
컨테이너 런타임은 이러한 스트림을 파일로 전달하고, `docker logs <container id>` 명령을 통해 컨테이너 로그를 가져온다.<br>
파드 로그는 로컬 머신에서 `kubectl logs kubia-manual` 명령어를 통해 확인할 수 있다. 파드가 삭제되면 로그도 함께 삭제된다.<br>
파드가 삭제된 후에도 파드의 로그를 보기 위해서는 모든 로그를 중앙 저장소에 저장하는 클러스터 전체의 중앙집중식 로깅을 설정해야 한다.

서비스를 거치지 않고 특정 파드와 대화하고 싶을 때 쿠버네티스는 해당 파드로 향하는 port forwarding을 구성해준다.<br>
포트 포워딩 구성은 `kubectl port-forward` 명령으로 할 수 있다. 포트 포워딩을 통해 다른 터미널에서 curl을 이용해 localhost:8888에서 실행되고 있는 kubectl port-forward 프록시를 통해 HTTP 요청을 해당 파드에 보낼 수 있다.

## 3.3 레이블을 이용한 파드 구성

파드 수가 증가함에 따라 파드를 부분 집합으로 분류할 필요가 있다. 레이블을 통해 파드와 기타 다른 쿠버네티스 오브젝트의 조직화가 이뤄진다.<br>
레이블은 리소스에 첨부하는 키-값 쌍으로, 이 쌍은 레이블 셀렉터를 사용해 리소스를 선택할 때 활용된다.<br>
`kubectl get pods` 명령어에 `--show-labels` 스위치를 사용해 레이블을 볼 수 있다. 일부 레이블만 보고 싶다면 해당 레이블을 `-L <레이블>`로 지정해 각 레이블을 자체 열에 표시할 수 있다.<br>
기존파드에 레이블을 추가하거나 수정할 수 있으며, 기존에 가지고 있던 레이블을 변경하기 위해서는 `--overwrite` 옵션이 필요하다.

<br>

## 3.4 레이블 셀렉터를 이용한 파드 부분 집합 나열

레이블 셀렉터는 특정 레이블로 태그된 파드의 부분 집합을 선택해 원하는 작업을 수행한다.
레이블 셀렉터는 리소스 중에서 다음 기준에 따라 리소스를 선택한다.
- 특정한 키를 포함하거나 포함하지 않는 레이블
- 특정한 키와 값을 가진 레이블
- 특정한 키를 갖고 있지만, 다른 값을 가진 레이블

!, in 등 연산자를 통해 선택할 수 있다. 또한 셀렉터는 쉼표로 구분된 여러 기준을 포함하는 것도 가능하다.

<br>

## 3.5 레이블과 셀렉터를 이용해 파드 스케줄링 제한

쿠버네티스의 전체적인 아이디어는 그 위에 실행되는 애플리케이션으로부터 실제 인프라를 숨기는 것에 있기에, 파드가 어떤 노드에 스케줄링되어야 하는지 구체적으로 지정하면 애플리케이션이 인프라에 결합되는 문제가 발생한다.<br>
따라서 정확한 노드를 지정하는 대신 필요한 노드 요구 사항을 기술하고 노드 레이블과 레이블 셀렉터를 통해 쿠버네티스가 요구 사항을 만족하는 노드를 선택하도록 한다.<br>
레이블은 노드를 포함한 모든 쿠버네티스 오브젝트에 부착할 수 있다. yaml 명세에서 `spce` 부분의 `nodeSelector: <label-name>: "true"`로 작성하면 파드를 새엇ㅇ할 때, 스케줄러는 `gpu=true` 레이블을 가지고 있는 노드 중에서 선택한다.

<br>

## 3.6 파드에 어노테이션 달기

파드 및 다른 오브젝트는 레이블 외에 어노테이션을 가질 수 있다. 어노테이션은 키-값 쌍으로 레이블과 거의 비슷하지만 식별 정보를 갖지 않는다.<br>
어노테이션은 tools에서 주로 사용되는데, 쿠버네티스에 새로운 기능을 베타 버전으로 추가할 때 어노테이션을 사용하고 변경 사항이 명확해지면 이때 필드로 변경된다.<br>
어노테이션이 유용하게 사용되는 경우는 파드나 다른 API 오브젝트에 설명을 추가해 두는 것이다. 이렇게 하면 클러스터를 사용하는 모든 사람이 개별 오브젝트에 관한 정보를 신속하게 찾아볼 수 있다.<br>
`kubectl annotate` 명령을 사용해 어노테이션을 추가할 수 있다. 어노테이션을 추가할 때 고유한 접두사를 사용하지 않으면 다른 도구나 라이브러리가 오브젝트에 어노테이션을 추가하면서 기존에 있던 어노테이션을 덮어버릴 수 있다. 따라서 키 충돌 방지를 위해 추가 시 `"foo bar"`를 키 값으로 넣는 것이 좋다.

<br>

## 3.7 네임스페이스를 사용한 리소스 그룹화

각 오브젝트는 여러 레이블을 가질 수 있기 때문에 오브젝트 그룹은 서로 겹쳐질 수 있고, 클러스터에서 작업을 수행할 때 레이블 셀렉터를 명시적으로 지정하지 않으면 항상 모든 오브젝트를 보게 된다.<br>
쿠버네티스는 오브젝트를 네임스페이스로 그룹화해 오브젝트 이름의 범위를 제공한다. 리소스를 여러 네임스페이스로 분할해 같은 리소스 이름을 다른 네임스페이스에 걸쳐 여러 번 사용할 수 있게 해준다.<br>
여러 네임스페이스를 사용하면 많은 구성 요소를 가진 복잡한 시스템을 좀 더 작은 개별 그룹으로 분리할 수 있다. 또한 멀티테넌트 환경처럼 리소스를 분리하는 데 사용된다.<br>
단, 노드 리소스는 global이며 단일 네임스페이스에 얽매이지 않는다.

`kubectl get ns`로 네임스페이스의 목록을 확인할 수 있고 `--namespace <ns명>` 명령어를 통해 해당 네임스페이스에서 kubectl 명령어를 통해 작업이 가능하다.<br>
네임스페이스는 리소스를 격리하는 것 외에도 특정 사용자가 지정된 리소스에 접근할 수 있도록 허용하고, 개별 사용자가 사용할 수 있는 컴퓨팅 리소스를 제한하는 데에도 사용된다.<br>
네임스페이스는 다른 것과 마찬가지로 쿠버네티스 리소스이기 때문에 yaml 파일을 쿠버네티스 API 서버에 요청해 생성할 수 있다. 또한 `kubectl create namespace <ns-name>` 명령어로도 생성 가능하다.<br>
네임스페이스를 사용하면 오브젝트를 별도 그룹으로 분리해 특정한 네임스페이스 안에 속한 리소스를 대상으로 작업할 수 있게 해주지만, 실행 중인 오브젝트에 대한 격리는 제공하지 않는다.<br>
네임스페이스에서 네트워크 격리를 제공하는지는 쿠버네티스와 함께 배포하는 네트워킹 솔루션에 따라 다르다.

<br>

## 3.8 파드 중지와 제거

`kubectl delete po kubia-gpu` 명령을 통해 파드를 삭제할 수 있고, 파드를 삭제하면 쿠버네티스는 파드 안에 있는 모든 컨테이너를 종료하도록 지시한다.<br>
쿠버네티스는 SIGTERM 신호를 프로세스에 보내고 지정된 시간(기본값 30초) 동안 기다린다. 시간 내에 종료되지 않으면 SIGKILL 신호를 통해 종료한다.<br>
이름 외에도 레이블 셀렉터를 통해 제거할 수도 있다. 단, 레플리케이션컨트롤러를 통해 만들어진 파드는 desire 값에 맞게 개수를 유지하려고 하므로 해당 파드들을 삭제하기 위해서는 desired 값을 0으로 수정하거나, 레플리케이션컨트롤러도 삭제해야 한다.
