# 4. 레플리케이션과 그 밖의 컨트롤러: 관리되는 파드 배포

파드를 직접 생성하는 대신 레플리케이션컨트롤러 또는 디플로이먼트와 같은 유형의 리소스를 생성해 실제 파드를 생성하고 관리한다.

<br>

## 4.1 파드를 안정적으로 유지하기

파드가 노드에 스케줄링되는 즉시, 해당 노드의 kubelet은 파드의 컨테이너를 실행하고 파드가 존재하는 한 컨테이너가 계속 실행되도록 할 것이다.<br>
crash가 발생해도 kubelet이 컨테이너를 다시 시작하므로, 쿠버네티스에서 애플리케이션을 실행하는 것만으로도 자동으로 치유할 수 있는 능력이 주어진다.<br>
그러나 자바에서 메모리 누수가 있어 OOM Error가 발생한다고 하더라도 JVM 프로세스는 계속 실행된다. 또는 애플리케이션이 무한 루프나 교착 상태에 빠져서 응답을 하지 못하는 상황에서는 쿠버네티스가 애플리케이션을 다시 시작하지 못한다.

쿠버네티스는 **liveness probe**를 통해 컨테이너가 살아있는지 확인할 수 있다. liveness probe는 파드의 spec에 지정할 수 있다.<br>
쿠버네티스는 주기적으로 probe를 실행하고, probe가 실패할 경우 컨테이너를 다시 시작한다.
- HTTP GET probe: 지정한 IP 주소, 포트, 경로에 HTTP GET 요청 수행, 응답 코드가 오류를 나타내지 않는 경우 probe 성공 간주
- TCP socket probe: 컨테이너의 지정된 포트에 TCP 연결 시도, 연결에 성공하면 probe 성공 간주
- Exec probe: 컨테이너 내의 임의의 명령을 실행하고 명령의 종료 상태 코드 확인, 상태 코드가 0이면 probe 성공 간주

<br>

liveness probe 옵션에는 에러 코드 뿐만 아니라 delay, timeout, period 등과 같은 추가 속성을 기준으로도 실행할 수 있다.<br>
초기 지연을 설정하지 않으면 대부분의 애플리케이션은 요청을 받을 준비가 되어 있지 않아 probe가 실패하고, 컨테이너가 다시 시작될 수 있음에 유의해야 한다.<br>
공식 문서: https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/

더 나은 liveness probe를 위해 특정 URL 경로(/health)에 요청하도록 probe를 구성해 애플리케이션 내에서 실행 중인 모든 주요 구성 요소가 살아 있는지 또는 응답이 없는지 확인하도록 구성할 수 있다.<br>
liveness probe는 애픍리케이션의 내부만 체크하고 외부 요인의 영향을 받지 않도록 해야 한다.<br>
근본적인 원인이 외부에 있는 경우 컨테이너를 재시작한다 하더라도 문제가 해결되지 않기 때문이다.<br>
또한 liveness probe는 자주 실행하되, 1초 이내에 완료돼야 한다. probe가 사용하는 CPU 시간은 컨테이너의 CPU 시간 할당량으로 계산되므로 liveness probe를 무겁게 만들면 메인 애플리케이션 프로세스에서 사용할 수 있는 CPU 시간이 줄어들게 되기 때문이다.<br>
probe는 실패 임계값을 1로 설정하더라도 k8s는 probe를 여러 번 재시도하므로 probe에 자체적인 재시도 루프를 구현할 필요는 없다.<br>
노드 자체에 크래시가 발생한 경우 노드에서 실행되는 kubelet 대신 control plane이 대체 파드를 생성해야 한다.

<br>

## 4.2 레플리케이션컨트롤러 소개

레플리케이션 컨트롤러는 어떤 이유에서든 클러스터에서 노드가 사라지거나 노드에서 파드가 제거된 경우, 사라진 파드를 감지해 교체 파드를 생성한다.<br>
레플리케이션컨트롤러는 실행 중인 파드 목록을 지속적으로 모니터링하고, 특정 타입의 실제 파드 수가 의도하는 수와 일치하는지 항상 확인한다.<br>
파드가 너무 적게 실행 중인 경우 파드 템플릿에서 새 복제본을 만들고, 너무 많은 파드가 실행 중이면 초과 복제본이 제거된다.<br>
레플리케이션컨트롤러는 파드 유형이 아니라 특정 label selector와 일치하는 파드 세트에 작동된다.

레플리케이션컨트롤러에는 세 가지 필수 요소가 있다.
- label selector: 레플리케이션컨트롤러의 범위에 있는 파드를 결정
- replica count: 실행할 파드의 desired 수 지정
- pod template: 새로운 파드 레플리카 생성

레이블 셀렉터와 파드 템플릿을 변경해도 기존 파드에는 영향을 미치지 않는다. 레이블 셀렉터의 변경은 기존 파드에 대한 관리를 중지하고, 템플릿은 새 파드를 생성할 때만 영향을 미친다.

레플리케이션컨트롤러를 사용하면 다음과 같은 장점이 있다:
- 기존 파드가 사라지면 새 파드를 시작해 파드가 항상 실행되도록 한다.
- 클러스터 노드에 장애가 발생하면 장애가 발생한 노드에서 실행 중인 모든 파드에 관한 교체 복제본이 생성된다.
- 수동 또는 자동으로 파드를 쉽게 수평으로 확장할 수 있게 한다.

<br>

[레플리케이션컨트롤러 yaml 파일](files/rc.yaml)을 API 서버에 게시하면, 쿠버네티스는 레이블 셀렉터 `app=kubia`와 일치하는 파드 인스턴스가 3개를 유지하도록 하는 kubia라는 이름의 새로운 RC를 생성한다.<br>
템플릿의 파드 레이블은 RC의 레이블 셀렉터와 완전히 일치해야 한다. 셀렉터를 지정하지 않는 것도 가능하며, 이때는 템플릿의 레이블로 자동 설정된다.<br>
컨트롤러는 삭제 그 자체에 대한 대응이 아니라 결과적인 상태(부족한 파드 수)에 대응하는 것이다.<br>
RC는 삭제되는 파드에 대해 즉시 통지를 받고, 이 통지가 트리거가 되어 컨트롤러가 실제 파드 수를 확인한 뒤 적절한 조치를 취한다.<br>
파드가 오작동하는 경우, 파드를 레플리케이션컨트롤러의 범위 밖으로 빼내 컨트롤러가 새 파드로 교체하도록 한 다음 원하는 방식으로 파드를 디버그하거나 문제를 재연해볼 수 있다.
또한 레플리케이션컨트롤러의 파드 템플릿을 편집해 컨테이너 이미지를 변경하고 기존 파드를 삭제함으로써 새로운 템플릿을 사용해 기존 파드를 새로운 파드로 업그레이드하는 데 사용할 수 있다. (단, 더 나은 방법이 있다.)<br>
파드 수를 늘리거나 줄이는 것은 레플리케이션컨트롤러 리소스의 replicas 필드 값을 변경하기만 하면 된다.<br>
레플리케이션컨트롤러를 삭제하면 파드도 삭제되지만, 레플리케이션컨트롤러만 삭제하고 파드는 실행 상태로 두는 것도 가능하다.

<br>

## 4.3 레플리케이션컨트롤러 대신 레플리카셋 사용하기

레플리카셋은 레플리케이션컨트롤러와 똑같이 동작하지만 좀 더 풍부한 표현식을 사용하는 파드 셀렉터를 갖고 있다.<br>
레플리케이션컨트롤러의 레이블 셀렉터는 특정 레이블이 있는 파드만을 매칭시킬 수 있는 반면, 레플리카셋의 셀렉터는 특정 레이블이 없는 파드나 레이블의 값과 상관없이 특정 레이블의 키를 갖는 파드를 매칭시킬 수 있다.

레플리카셋의 주요 개선 사항은 좀 더 표현적인 레이블 셀렉터다.<br>
[레플리카셋 yaml 파일](files/replicaset.yaml)을 확인해보면 단순히 `matchLabels` 셀렉터뿐만 아니라 `matchExpressions`를 통해 셀렉터에 표현식을 추가할 수 있다.
- In: 레이블의 값이 지정된 값 중 하나와 일치
- NotIn: 레이블의 값이 지정된 값과 일치 X
- Exists: 파드에 지정된 키를 가진 레이블을 포함
- DoesNotExist: 파드에 지정된 키를 가진 레이블 포함 X

<br>

## 4.4 데몬셋을 사용해 각 노드에서 정확히 한 개의 파드 실행하기

노드에서 로그 수집기와 리소스 모니터 혹은 kube-proxy의 경우 클러스터의 모든 노드에, 노드당 하나의 파드만 실행되어야 한다.<br>
쿠버네티스를 사용하지 않는 환경에서는 일반적으로 노드가 부팅되는 동안에 시스템 초기화 스크립트 또는 systemd 데몬을 통해 시작된다.<br>
쿠버네티스 노드에서도 systemd를 사용해 시스템 프로세스를 실행할 수도 있지만, **DaemonSet** 오브젝트를 생성해 모든 클러스터 노드마다 파드를 하나만 실행할 수 있다.<br>
데몬셋에 의해 생성되는 파드는 타깃 노드가 이미 지정돼 있고 쿠버네티스 스케줄러를 건너뛰는 것을 제외하면 RC나 ReplicaSet과 매우 유사하다.<br>
데몬셋은 파드 셀렉터와 일치하는 파드 하나가 각 노드에서 실행 중인지 확인하는 것이 수행 역할이므로 복제본 개념이 필요하지 않다.<br>
데몬셋은 노드가 다운되는 경우에는 작업하지 않지만 새 노드가 클러스터에 추가되면 즉시 새 파드 인스턴스를 새 노드에 배포한다.<br>
[데몬셋 yaml 파일](files/daemonset.yaml)을 확인하면 파드 템플릿에서 `node-Selector` 속성을 지정하면 일부 노드에만 파드를 배포할 수 있다.

## 4.5 완료 가능한 단일 태스크를 수행하는 파드 실행

완료 가능한 태스크(completable task)에서는 프로세스가 종료된 후에 다시 시작될 필요가 없다.<br>
쿠버네티스는 job을 이용해 컨테이너 내부에서 실행 중인 프로세스가 성공적으로 완료되면 컨테이너를 다시 시작하지 않는 파드를 실행한다.<br>
노드에 장애가 발생한 경우 해당 job이 관리하는 파드는 다른 노드로 다시 스케줄링되고, 프로세스 자체에 장애가 발생한 경우 job에서 컨테이너를 다시 시작할 것인지 설정 가능하다.<br>
job은 작업이 제대로 완료되는 것이 중요한 임시 작업에 유용하다. 예시로는 데이터를 어딘가에 저장하고 있고, 이 데이터를 변환해서 어딘가로 전송해야 하는 경우가 있다.<br>
[job yaml 파일](files/exporter.yaml)을 확인하면 잡 파드는 무한정 실행하지 않으므로 restartPolicy를 기본 정색(Always)로 사용하지 못하고 `Onfailure`나 `Never`로 명시적으로 설정해야 한다.<br>
`completions` 설정을 통해 job을 n번 실행할 수 있고, `parallelism` 설정을 통해 병령로 실행할 파드 수를 지정할 수 있다. `parallelism` 설정은 job이 실행되는 동안 변경 가능하다.<br>
파드 스펙에 `activeDeadlineSeconds` 속성을 설정해 파드의 실행 시간을 제한할 수 있다. 파드가 이보다 오래 실행되면 시스템이 종료를 시도하고 잡을 실패한 것으로 표시한다.

<br>

## 4.6 잡을 주기적으로 또는 한 번 실행되도록 스케줄링하기

많은 배치 잡이 미래의 특정 시간 또는 지정된 간격으로 반복 실행해야 할 때 리눅스나 유닉스 같은 운영체제에서는 cronjob으로 처리한다. 쿠버네티스에서도 지원한다.<br>
[cronjob yaml 파일](files/cronjob.yaml)처럼 스케줄에 따라 JobTemplate 특성에 맞는 잡 리소스를 생성한다.<br>
잡이나 파드가 상대적으로 늦게 실행될 수 있으며, `startingDeadlineSeconds` 필드를 지정해 데드라인을 설정할 수 있다.<br>
일반적인 상황에서 크론잡은 스케줄에 설정한 각 실행에 항상 하나의 잡만 생성하지만 두 개의 잡이 동시에 생성되거나 전혀 생성되지 않을 수 있다. 첫 번째 문제를 해결하려면 잡이 멱등성을 가져야 하고, 두 번째 문제점을 해결하려면 다음 번 잡 실행이 이전의 누락된 실행에서 완료했어야 하는 작업을 수행하는지 확인해야 한다.
